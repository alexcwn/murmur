Murmur  /  Internals

How a held key becomes text

Murmur is push-to-talk dictation for macOS. Hold Fn, speak, release, and cleaned-up text lands at your cursor in whatever app is focused. It ships no speech model and has no dependencies — macOS 26 does the AI, and Murmur is the plumbing that makes it feel like a product.

The engine question

Most dictation projects begin by downloading a Whisper checkpoint. This one never does.

The recognizer is Apple's SpeechAnalyzer, introduced in macOS 26 — the same engine behind Notes, Voice Memos and Journal.

The neural model is downloaded and version-managed by the operating system and shared across every app that asks for it. Murmur queries AssetInventory at launch, and either the model is already installed or the OS fetches it once. Recognition then runs entirely on-device.

So the interesting question isn't which model — it's the division of labour. Almost everything hard about speech is a framework call. Almost everything hard about the product is yours.

macOS provides

  • SpeechTranscriber — the recognizer, run in .progressiveTranscription mode so partial results stream while you speak
  • SpeechAnalyzer — coordinator that consumes an async stream of audio buffers
  • AssetInventory — model download and versioning
  • Foundation Models — the ~3B on-device LLM that does the cleanup pass

Murmur provides

  • Modifier-hold detection — a listen-only CGEventTap, because no hotkey API can express "held"
  • A permanently warm microphone with an audio-thread-safe gate
  • Focus-preserving HUD that renders above full-screen apps
  • Text injection into arbitrary apps, native or Electron
  • Prompt design for cleanup that doesn't rewrite your voice

The pipeline

Seven stages from keypress to inserted text. Filled boxes are macOS frameworks; outlined boxes are Murmur's own code.

One dictation, end to end

What actually happens, in order.

  1. launch

    Everything expensive happens before you press anything

    The speech model is confirmed present, AVAudioEngine starts and installs a tap on the microphone, and the CGEventTap begins watching for your hotkey. Doing any of this on the keypress would cost 150–300 ms every single time.

  2. key ↓

    A modifier-hold is detected

    The tap sees a flagsChanged event carrying keycode 0x3F. It observes but never swallows the event, so Fn keeps doing its normal job. Murmur records which app was frontmost — that decides the register later — and opens the audio gate.

  3. holding

    Audio streams, and transcription is already running

    The mic tap fires on a real-time audio thread roughly every 2048 samples. Each buffer is copied — CoreAudio reuses its own, so passing the original across a thread boundary would corrupt it — resampled to the analyzer's preferred format, and pushed into an AsyncStream.

    The analyzer consumes that stream and emits partial transcripts continuously. This is what updates live in the HUD, and it is the reason release feels instant.

  4. key ↑

    Only the tail is left to finalize

    The stream closes and finalizeAndFinishThroughEndOfInput() flushes the last fragment. Everything before it was transcribed while you were still talking. What comes out is unpunctuated and honest:

    um so i think we should ship it tuesday no wait wednesday

  5. cleanup

    An on-device LLM makes it read like writing

    Foundation Models strips fillers, adds punctuation, resolves the self-correction, and matches the tone of wherever you're typing — Gmail gets email register, a code editor gets something terser. The prompt is deliberately narrow: a model given latitude to "improve" text rewrites your voice, which is the fastest way to lose trust in a dictation tool.

    So I think we should ship it Wednesday.

  6. insert

    Two strategies, cheapest first

    Accessibility is tried first — setting AXSelectedText on the focused element replaces a selection correctly and never touches your clipboard. It works in native apps and is unreliable in Electron and web views, so the fallback is the pasteboard plus a synthesized ⌘V, with your previous clipboard saved and restored around it.

  7. +30s

    The microphone is released

    A permanently running engine keeps macOS's orange "mic in use" indicator lit, which makes a dictation app feel like it's always listening. After 30 seconds idle the engine stops while the tap stays installed, so a burst of dictations all stay instant and only the first after a pause pays the restart.

Why streaming, not recording

The single decision that most affects how the app feels. Both approaches transcribe the same audio — they differ in when.

Two seams

The pipeline talks to protocols, not to Apple. Both current implementations are one class each.

Swapping either means writing one new conforming class — nothing else changes.
ProtocolTodayCould become
TranscriptionEngine Apple SpeechAnalyzer Parakeet TDT via FluidAudio (Neural Engine, faster on Apple Silicon), or WhisperKit for wider multilingual coverage
TextFormatter Foundation Models, on-device A cloud model for Command Mode and a high-quality tier, kept off by default

The seams exist because the right engine is a question about your machine, your language and your latency tolerance — not something to decide once and bake in.

Three constraints that shaped the code

Each of these is a decision that looks arbitrary until it bites.

Audio thread

AudioCapture is nonisolated, deliberately

The package sets defaultIsolation(MainActor). Without the opt-out, the audio tap closure inherits MainActor isolation, and Swift 6 emits an executor assertion inside it. AVAudioEngine invokes that closure on a real-time audio thread, so the assertion fails and kills the process — dispatch_assert_queue → SIGTRAP — the instant the first buffer arrives.

It produces no crash report, and it does not reproduce when the binary is run from a terminal. Removing that keyword brings it back.

Focus

The HUD must never become key

It is a .nonactivatingPanel with canBecomeKey forced false, at .statusBar level so it floats above full-screen apps. If the panel takes key focus, the text field you were typing in loses its cursor and the injection lands nowhere.

Distribution

Not sandboxed, and it cannot be

The App Sandbox denies both global event taps and the Accessibility APIs — the two things the app is built on. A sandboxed build can neither see the hotkey nor insert text, which rules out the Mac App Store. Developer ID plus notarization is the distribution path.

Related: macOS keys permission grants to bundle ID and code signature, so ad-hoc signing silently drops every grant on each rebuild. One stable self-signed identity is why you approve permissions once instead of forever.
